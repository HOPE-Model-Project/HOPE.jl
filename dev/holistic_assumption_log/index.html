Holistic Linkage Assumption and Decision Log

Status: Living document Last updated: 2026-10-20

Purpose

This is the living human-readable register for assumptions and design decisions that affect information exchange between HOPE models. It currently focuses on GTEP-to-PCM physical realization and will later include GTEP-to-DART and PCM-to-DART entries.

The log complements, but does not replace, machine-readable case settings, physical-realization contracts, manifests, source registers, and run audits. Those artifacts remain the executable source of truth. This page explains why the current rules exist, what evidence supports them, and which gaps remain.

Status vocabulary

StatusMeaning
ValidatedImplemented and exercised by a solved or automated validation case

ProposedAgreed direction that is not yet implemented
OpenA known decision or data gap still requiring resolution
SupersededRetained for history but replaced by a later entry

Maintenance rule

Every material cross-model assumption should receive a stable HLA-### ID. When behavior changes, update its status and append a dated history entry. Do not silently delete a prior decision. Code, case manifests, validation reports, issues, and agent-run manifests should reference these IDs where practical.

At minimum, a new entry records:

  • the models and cases it affects;
  • whether it is data, formulation, realization, validation, or computing policy;
  • the current rule and rationale;
  • its evidence or implementation location;
  • its consequence and planned resolution.

Detailed entries

HLA-001 — spatial roles

  • Scope: Maryland 20% RPS full-year GTEP-to-PCM benchmark.
  • Rule: GTEP makes planning decisions over APS_MD, BGE, DPL_MD, PEPCO, and EXT. PCM tests their physical operation on 656 buses and 838 branches.
  • Rationale: Planning aggregation is a human and computational choice; PCM retains the network detail required to expose intra-zonal constraints.
  • Evidence: case manifests, HOPE_physical_realization.yml, and the holistic handoff audit.
  • Consequence: A feasible zonal plan is not guaranteed to be nodally deliverable, so physical realization and a PCM screen remain necessary.

HLA-002 — existing asset identity

  • Rule: Asset_ID is nonblank and unique in both stages and is used before any legacy row or aggregate mapping.
  • Rationale: Row numbers are unstable under sorting, aggregation, or source updates.
  • Evidence: all 271 existing Maryland generators crosswalk successfully.
  • Next action: extend the same stable identity convention to every future storage and transmission source where it is not already available.

HLA-003 and HLA-004 — candidate location

  • Rule: GTEP remains zonal, but each generation and storage candidate carries Planning_Zone, Bus_id, and Candidate_ID. The current Maryland case uses the largest existing generation bus in each planning zone.
  • Rationale: This makes the linkage deterministic while higher-quality interconnection and land/resource data are unavailable.
  • Evidence: references/candidate_bus_mapping.csv and candidate input rows.
  • Consequence: All technologies in a zone currently share one representative bus. This is a transparent test assumption, not optimized or observed siting.
  • Next action: define a candidate-bus catalog with technology eligibility, bus capacity, siting cost, evidence, and confidence, then add a deterministic allocation or siting optimization step.

HLA-005 — plant and unit size

  • Rule: The solved continuous GTEP capacity becomes one aggregate PCM row unless the candidate supplies PCM_Unit_Size_MW.
  • Rationale: Preserve compatibility with existing continuous GTEP cases while supporting explicit unit disaggregation when physical detail is available.
  • Evidence: realize_generation_builds in src/holistic_linkage.jl and the generation-build audit.
  • Consequence: Without PCM_Unit_Size_MW, a thermal build is one committed aggregate row even when it represents several physical units. This is useful for linkage testing but is not a production-grade plant fleet.
  • Next action: choose technology-specific unit sizes and commitment behavior through the template registry proposed in HLA-008.

HLA-006 through HLA-008 — parameter ownership

  • Existing resources: GTEP and PCM keep their own source tables. They share a common fleet basis in this benchmark, and Asset_ID maps capacity retirements. The linkage does not replace PCM costs, commitment, ramp, reserve, outage, or emissions parameters for existing resources.
  • New resources: candidate-supplied values are copied first. The candidate's Operational_Template_ID then selects a row from the PCM-owned optional operational_resource_templates.csv. Remaining numeric fields use the same zone/type, then the same type, then code defaults.
  • Thermal commitment safeguard: every newly realized row with Flag_thermal = 1 receives Flag_UC = 1, even when a legacy candidate carries a zero placeholder. Existing PCM resources are not modified by this rule.
  • Evidence: the Maryland annual benchmark defines modern NGCC, solar, wind, and four-hour battery templates. The realized-input package writes operational_parameters_audit.csv with field-level candidate, template, and thermal-policy sources.
  • Remaining refinement: technology-specific unit size and minimum-output fractions should be calibrated before treating aggregate GTEP builds as a production physical fleet.

HLA-009 and HLA-010 — retirement and transmission

  • Retirement: proportional physical capacity is the default. Optional largest-first, smallest-first, or explicit-priority allocation and partial-unit rejection are implemented.
  • Transmission: Corridor_ID is preferred, followed by explicit PCM endpoints. Directional capacity conservation is audited.
  • Validation boundary: the annual Maryland result selected neither retirement nor transmission expansion. The restricted linkage benchmark exercises those paths; the annual case should not claim that it does.

HLA-011 — reserve translation

  • Rule: GTEP's single upward reserve product is 7% of load, equal to PCM's configured 1% REG-UP + 3% SPIN + 3% NSPIN requirements.
  • Rationale: Prevent aggregate planning from understating the upward capability required by the operational model.
  • Limitation: This aligns total upward capability, not product response time, eligibility, or co-optimization details.

HLA-012 and HLA-013 — validation horizon and policy

  • Rule: routine linkage validation uses annual GTEP followed by July PCM.
  • What it establishes: identity, capacity conservation, physical mapping, source immutability, PCM model construction, and operation of the transferred fleet under a demanding summer month.
  • What it does not establish: annual PCM cost, winter adequacy, seasonal storage, annual emissions, or annual REC compliance.
  • RPS interpretation: July independently satisfies 20% local RPS. This is a deliberately restrictive integration test, not an annual REC bank.

HLA-014 and HLA-015 — chronology inputs and boundary

  • Availability: use each generator's static AF and FOR because no identity-compatible annual outage chronology is available. Repeating the compact July outage pattern would create false annual evidence.
  • Interchange: scheduled nodal interchange is zero because no authoritative hourly schedule is assumed. Hourly boundary caps allow endogenous imports and exports through retained external interfaces.

HLA-016 and HLA-017 — physical-data fidelity

  • Observed/derived: OSM topology, locations, and tagged voltage where available.
  • Inferred/assumed: missing voltage, reactance, ratings, transformers, candidate siting, and the external corridor proxy.
  • Calibration: the four-zone plan produced one July shedding hour at an inferred 500 MW intra-PEPCO constraint. OSM_L1528639488 is therefore modeled at 600 MW in both directions. The adjustment remains labeled as a modeling assumption and must be revisited when authoritative data are available.

HLA-018 through HLA-020 — workflow and repository policy

  • Realization occurs in memory and is persisted under output_holistic/realized_inputs/.
  • Before/after source hashes must match.
  • The full annual PCM exceeded the 32 GB validation workstation during model construction; it is not claimed as solved. Route it to a higher-memory worker.
  • Exact rolling operation is future work because commitment, dispatch, storage state, and annual REC accounting must cross window boundaries.
  • Core transfer behavior belongs in src/. Agent launchers and diagnostics belong in tools/repo_utils/. Reproducible case builders belong in ModelCases/tools/. Generated run workspaces belong under ignored artifacts/agent_runs/.
